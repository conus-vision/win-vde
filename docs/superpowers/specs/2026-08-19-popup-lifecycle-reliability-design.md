# Virtual Desktop Extension Popup and Lifecycle Reliability Design

Дата: 2026-08-19

Статус: утверждено пользователем
База исходного кода: `main` на коммите `26481fc`; утверждённый design-документ
зафиксирован отдельным коммитом `e4ca435`.

## 1. Цель и границы

Доработать существующую Win32/C++ утилиту так, чтобы:

- popup независимо подсвечивал текущий виртуальный десктоп, выбранную цель и активное окно;
- `Ctrl+Click` переносил активное окно, переключал Windows на целевой десктоп и оставлял popup открытым;
- footer содержал корректный бренд и две ссылки;
- автоматическая раскладка надёжно отслеживала все окна Firefox, Chrome и Edge;
- закрытые окна сохранялись 30 календарных суток и восстанавливались при повторном появлении;
- старт, обычная работа, выход VDE и завершение сеанса Windows не теряли новые положения;
- повреждение файла, временный сбой браузера или COM не уничтожали последнюю исправную раскладку;
- периодический мониторинг и массовый restore не блокировали UI-поток;
- подтверждённые утечки GDI и неограниченный рост служебного состояния были устранены.

Автоматическое сохранение и восстановление относится только к включённым профилям Firefox, Chrome и Edge. Popup продолжает показывать и переносить остальные обычные окна Windows, но не сохраняет их между сеансами.

## 2. Подтверждённые проблемы текущей реализации

1. Формат v3 хранит `missingRuns` и удаляет запись после трёх подходящих выходов VDE, а не через 30 дней.
2. Один глобальный `LcState` получает агрегированный `AnyAppPresent()`. Поэтому появление Chrome при открытом Firefox или повторное появление одного окна при оставшемся втором окне не запускает restore.
3. После startup/launch restore код сразу принимает текущую подпись за сохранённую. Новые несовпавшие окна не попадают в auto-layout до следующего изменения или штатного выхода.
4. `MergeAutoLayout` индексирует записи одним fingerprint. Одинаковые окна схлопываются и не могут хранить разные назначения.
5. Popup использует `g_sel` одновременно как текущий десктоп и навигационный выбор; движение мыши уничтожает смысл подсветки текущего десктопа.
6. Активный `g_target` не сравнивается со строками окон, поэтому активное окно визуально не выделяется.
7. `Commit()` скрывает popup до переноса, а `WM_ACTIVATE/WA_INACTIVE` закрывает его при переключении десктопа.
8. Auto-layout пишется через `CREATE_ALWAYS`; ошибка записи может оставить обрезанный файл, а результат записи игнорируется.
9. Каждые пять секунд выполняются повторные перечисления окон и повторный разбор браузерных сессий на UI-потоке.
10. Проверка переноса использует до четырёх `Sleep(150)` на окно. Массовый restore способен заморозить UI на секунды.
11. При изменении размера popup старый bitmap удаляется, пока выбран в memory DC; `DeleteObject` не срабатывает и GDI-объекты накапливаются.
12. `g_seenKeys` растёт весь срок жизни процесса, а stale HWND проверяется только через `IsWindow`, чего недостаточно при переиспользовании handle.
13. mozLz4 принимает заявленный распакованный размер без верхней границы; частичный `ReadFile` ошибочно считается успехом; parser layout принимает некорректные GUID и числа.

Исходная тестовая база проходит `65/65`, но проверяет старую run-based grace-логику и happy paths, а не перечисленные сбои.

## 3. Архитектура

Рефакторинг остаётся целевым и не превращает приложение в отдельный сервис:

- `src/layout.hpp` — чистые структуры layout v4, сериализация, строгий parser, one-to-one matching, reconciliation и 30-дневная очистка;
- `src/layout_store.hpp` — Win32-загрузка, file mutex, backup и атомарная запись;
- `src/lifecycle.hpp` — чистые решения per-app/per-window: settle, restore-before-save, disappearance, retry и финальный snapshot;
- `src/picker_state.hpp` — чистое состояние текущего десктопа, выбранной цели, активного окна и сохранение UI-состояния при refresh;
- `src/session.hpp` — ограниченный и проверяемый Chromium parser плюс метаданные для кэша;
- `src/vde.cpp` — перечисление HWND, COM-переносы, таймеры, popup/tray и координация чистых модулей.

Win32/COM остаются в `vde.cpp`; решения, которые можно проверить без Explorer и реальных виртуальных десктопов, выносятся в заголовки и покрываются существующим тестовым executable.

## 4. Layout v4

### 4.1 Поля

Заголовок файла:

```text
# VDE snapshot v4
```

Строка десктопа сохраняет текущий v3-формат. Строка окна получает следующие логические поля:

```text
W app recordId deskIndex desktopGuid activeTitle activeDomain tabCount counts lastSeenUtc missingSinceUtc
```

- `recordId` — сгенерированный GUID, постоянная идентичность записи;
- `app` — только `firefox`, `chrome` или `msedge`;
- `desktopGuid` — основной адрес назначения;
- `deskIndex` — fallback и диагностическое поле, не основание для слепого переноса при неизвестном GUID;
- `activeTitle`, `activeDomain`, `tabCount`, `counts` — существующий fingerprint;
- `lastSeenUtc` — Unix time последнего подтверждённого наблюдения живого окна;
- `missingSinceUtc` — Unix time начала отсутствия, `0` для наблюдаемого окна.

Строковые пользовательские поля продолжают кодироваться Base64. Числа разбираются с проверкой диапазона и полного потребления строки. GUID, Base64, количество полей, версия и размер файла проверяются до публикации результата parser.

### 4.2 Срок хранения

Окно просрочено, когда:

```text
missingSinceUtc != 0 && nowUtc >= missingSinceUtc + 30 * 24 * 60 * 60
```

Граница ровно 30 суток считается просроченной. При обнаруженном исчезновении `missingSinceUtc` получает последнее подтверждённое `lastSeenUtc`; если корректного значения нет — текущий `nowUtc`. Повторное появление до expiry сбрасывает `missingSinceUtc` в `0`. После expiry окно удаляется, а появившийся позже HWND создаёт новую запись.

### 4.3 Миграция

- v2 и v3 читаются отдельными совместимыми ветками parser;
- каждой старой записи назначается новый `recordId`;
- `lastSeenUtc` устанавливается во время миграции;
- запись с ненулевым старым `missingRuns` получает `missingSinceUtc = nowUtc`, остальные — `0`;
- таким образом каждая мигрированная запись получает полный новый 30-дневный срок;
- исходный файл не заменяется до успешной сериализации, flush и атомарной установки v4;
- при невалидном исходнике переносы не выполняются и файл сохраняется для диагностики.

## 5. Идентичность и matching

### 5.1 Внутри работающего VDE

Для каждого захваченного окна хранится:

```text
HWND + PID + process creation time -> recordId
```

Перед переносом все три свойства сверяются повторно. Это предотвращает перенос постороннего окна после закрытия исходного HWND и переиспользования handle.

Изменение заголовка, вкладок или переход от title-only к domain fingerprint обновляет существующий `recordId`, а не создаёт бесконечные новые ключи.

### 5.2 Между запусками

- matching выполняется только внутри одного `app`;
- сохранённые и живые окна назначаются one-to-one;
- scoring сохраняет доменные, title и tab-count признаки текущей реализации;
- одинаковые fingerprints остаются отдельными элементами и не схлопываются map-индексом;
- полностью неразличимые дубликаты назначаются детерминированно, сохраняя количество назначений и десктопов;
- несовпавшее живое окно становится новой записью только после завершения restore-попытки.

## 6. Жизненный цикл

Автоматический жизненный цикл действует при включённом `Auto-save & auto-restore layout`. Ручные Save/Restore остаются доступными отдельно.

`layout-auto.txt` использует retention и reconciliation из этого раздела. `layout-manual.txt` также сериализуется как v4, но остаётся полным ручным checkpoint: монитор его не дополняет, не помечает missing и не очищает по сроку.

### 6.1 Старт VDE

1. Взять layout file mutex.
2. Загрузить и строго проверить v4 либо мигрировать v2/v3.
3. Восстановиться из backup, если основной файл повреждён, а backup валиден.
4. Создать независимое состояние для каждого включённого браузера.
5. Для уже открытых окон дождаться короткой стабилизации и выполнить one-to-one matching.
6. После matching пометить сохранённые записи без живой пары отсутствующими: если `missingSinceUtc == 0`, взять валидный `lastSeenUtc`, иначе текущий `nowUtc`.
7. Удалить записи, достигшие 30 суток, и поставить переносы совпавших живых окон в очередь.
8. После подтверждения переносов сохранить все живые окна. Новые несовпавшие окна сохраняются в текущих положениях в той же транзакции.

Отключённый в Settings браузер не помечается вновь отсутствующим и не участвует в matching. Его уже missing-записи продолжают подчиняться абсолютной 30-дневной границе.

### 6.2 Появление браузера или отдельного окна

- Firefox, Chrome и Edge имеют отдельные состояния присутствия;
- settle сбрасывается, если меняется количество HWND или релевантная версия browser session;
- restore начинается после двух одинаковых последовательных snapshots либо по достижении предельных 20 секунд;
- позднее окно, появившееся после первой волны browser restore, проходит тот же restore-before-save процесс отдельно;
- найденная сохранённая запись переносится до обновления её назначения;
- если перенос временно не подтверждён, сохранённое назначение не перезаписывается текущим десктопом.

### 6.3 Работа VDE

- один дешёвый snapshot за monitor tick содержит app, HWND, проверяемую identity и desktop GUID;
- diff обнаруживает появление, исчезновение и перемещение;
- пользовательский перенос сохраняется не позднее следующего monitor tick;
- перенос через popup для Firefox/Chrome/Edge сохраняется немедленно после подтверждения;
- session parser запускается только для нового/изменившегося окна, изменившегося файла сессии, restore или финального snapshot;
- присутствующее окно обновляет `lastSeenUtc` в памяти; disappearance и выход атомарно фиксируют состояние;
- при неизменной раскладке выполняется не чаще одного heartbeat-checkpoint за 6 часов, чтобы crash не оставлял месяцами устаревший `lastSeenUtc`, но монитор не писал файл каждые пять секунд;
- purge выполняется на старте, при reconciliation и при выходе, поэтому не зависит от наличия живых окон.

### 6.4 Выход и завершение Windows

Финальная транзакция идемпотентна и вызывается из обычного Exit/`WM_DESTROY`, а также из обработки `WM_QUERYENDSESSION`/`WM_ENDSESSION`:

1. Получить финальный snapshot всех доступных окон включённых браузеров.
2. Обновить живые записи и отметить новые исчезновения.
3. Не уничтожать сохранённое назначение окна из-за временной ошибки чтения.
4. Удалить записи с истёкшими 30 сутками.
5. Записать layout атомарно даже при нуле живых окон.

Повторный вызов во время одного shutdown не создаёт вторую конкурирующую транзакцию.

## 7. Очередь restore

`Sleep` удаляется из UI-потока. Координатор переносов работает сообщениями/таймером:

1. Проверить identity HWND.
2. Отправить move на сохранённый десктоп.
3. Через 150 мс проверить документированным `GetWindowDesktopId`.
4. Повторить не более четырёх раз.
5. Отметить success, transient failure или permanent failure.

Несколько окон обслуживаются малыми порциями между сообщениями, поэтому tray, popup и shutdown-сообщения продолжают обрабатываться. Успешный read-back разрешает обновление `lastSeenUtc` и snapshot. Ошибка сохраняет прежнее назначение и попадает в итоговую сводку; приложение не зацикливается.

## 8. Popup

### 8.1 Независимые состояния

- `currentDesktopGuid` получается через `GetCurrentDesktop` и не зависит от target HWND;
- `selectedDesktopGuid` меняется от hover, клавиатуры и выбранной цели;
- `activeTarget` хранит HWND, PID, process creation time и заголовок окна, которое было foreground перед открытием popup.

Текущий десктоп получает акцентную полупрозрачную подложку внутри tile. В GDI эффект реализуется детерминированным смешиванием accent и базового цвета, что даёт одинаковый результат в double buffer без отдельного alpha surface. Выбранная цель получает отдельный оранжевый контур. Строка `activeTarget` получает собственную полупрозрачную подложку и акцентную метку.

### 8.2 `Ctrl+Click`

1. Заблокировать повторную активацию и установить scoped-флаг controlled transition.
2. Повторно проверить target identity.
3. Перенести target на целевой десктоп.
4. Перенести принадлежащее VDE окно popup на тот же десктоп документированным API для собственного процесса.
5. Переключить Windows на целевой десктоп.
6. Не выполнять `HidePicker`; игнорировать `WA_INACTIVE` только во время controlled transition.
7. На новом десктопе восстановить topmost/focus popup.
8. Перестроить модель, сохранив поисковый текст, активность поиска, выбранный GUID и scroll каждого tile по GUID.
9. Обновить current-desktop underlay и переместить highlighted active row в целевой tile.
10. Немедленно сохранить новое положение, если target относится к Firefox, Chrome или Edge.

При ошибке move переключение не выполняется, popup остаётся открыт, а подсветка не показывает несуществующее состояние. После ошибки показывается краткое неблокирующее сообщение.

Общий путь `ctrlMove` используется также клавиатурными Ctrl+Enter/Ctrl+Space, чтобы мышь и клавиатура не расходились по поведению.

### 8.3 Остальные действия

- обычный click/Enter переключает десктоп и закрывает popup, как раньше;
- `Esc` и обычная потеря активации закрывают popup;
- поиск по всем вкладкам, wheel-scroll и tooltip сохраняются;
- refresh после monitor-события не стирает UI-состояние.

### 8.4 Footer и branding

Под сеткой tiles, внутри нижней части popup, рисуется:

```text
Virtual Desktop Extension for Windows 11 by Volodymyr Moskvin (c) 2026 Conus Vision
```

- текст `Virtual Desktop Extension` — ссылка на `https://github.com/conus-vision/win-vde`;
- текст `Conus Vision` — ссылка на `https://conus.vision`;
- ссылки имеют визуальный hover, hand cursor и отдельные hit rectangles;
- открытие ссылки использует `ShellExecuteW` и может закрыть popup обычной потерей активации;
- видимые `Virtual Desktops Extention`/`Extention` исправляются на `Virtual Desktop Extension`;
- каталог `%LOCALAPPDATA%\VirtualDesktopsExtention` и существующие registry keys сохраняют legacy spelling для совместимости.

## 9. Надёжное хранилище

### 9.1 Атомарная запись

1. Сериализовать полностью в память.
2. Создать временный файл в каталоге layout.
3. Проверить полный `WriteFile` и вызвать `FlushFileBuffers`.
4. Сохранить последнюю валидную версию как `.bak`.
5. Установить новый файл через `ReplaceFileW` либо `MoveFileExW` с `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH` для первого файла.
6. Только после успеха обновить last-saved signature и очистить dirty state.

При любой ошибке старый layout остаётся рабочим, dirty state сохраняется для retry, а пользователь получает краткое уведомление.

### 9.2 Конкуренция

- named mutex запрещает вторую tray-копию VDE;
- отдельный named layout mutex сериализует tray и CLI-команды;
- lock удерживается только на read-modify-write транзакцию, не на весь срок жизни процесса.

### 9.3 Ограничения и валидация

- layout file: максимум 16 MiB и ограниченное число records;
- browser session input и распакованный mozLz4: максимум 512 MiB;
- изменение размера/mtime во время чтения считается нестабильным snapshot и повторяется один раз на следующем цикле;
- любой mid-read failure возвращает ошибку, а не частичный успех;
- invalid layout не публикует частично разобранные записи;
- при отсутствии документированного `IVirtualDesktopManager` зависящие функции переходят в явный degraded mode, а verify не возвращает ложный success.

## 10. Производительность и ресурсы

- `EnumWindows` и desktop lookup выполняются один раз на monitor tick, результат переиспользуется lifecycle и signature;
- Firefox/Chromium sessions кэшируются по полному пути, размеру и mtime;
- search использует готовый кэш всех вкладок и пересчитывает filtered rows на `EN_CHANGE`, а `Paint` только рисует;
- получение icon сначала использует дешёвые class/window данные, затем один короткий `SendMessageTimeout`; результаты кэшируются на срок валидности identity;
- GDI double buffer хранит original bitmap, выбирает replacement до удаления старого bitmap и освобождает bitmap/DC при shutdown;
- picker fonts, search font, созданные brushes и принадлежащие приложению icons освобождаются при завершении;
- `g_seenKeys` заменяется конечным набором текущих records и per-window identity;
- UI message loop не содержит ожиданий verify и многосекундных циклов restore.

## 11. Обработка ошибок

- corrupt primary + valid backup: использовать backup, сообщить о восстановлении, не выполнять переносы из corrupt данных;
- corrupt primary и backup: переименовать сохранённые байты в диагностические `.corrupt-<UTC>` копии, начать пустое in-memory состояние и показать предупреждение; новые данные не затирают диагностические копии;
- transient browser-session read: сохранить старые fingerprints/назначения и повторить позже;
- failed COM move: не менять сохранённый destination, ограниченно повторить и показать итог;
- target identity mismatch: отменить только пользовательский перенос, не затрагивать popup или layout;
- atomic write failure: оставить старый файл и dirty state;
- unknown desktop GUID: не переносить окно на индекс `0`; считать запись unresolved и отразить в сводке.

## 12. Тестирование

Новая production-логика создаётся по RED-GREEN-REFACTOR. Сначала добавляется падающий тест, подтверждается ожидаемая причина падения, затем минимальная реализация.

### 12.1 Автоматические тесты

- v4 round-trip, strict GUID/integer/Base64 parsing и транзакционность parser;
- миграция v2 и v3, выдача `recordId` и полный 30-дневный срок;
- retention: 29 дней, ровно 30 дней, возврат до expiry, появление после expiry;
- Firefox остаётся открытым, пока появляется Chrome;
- одно окно Firefox остаётся, второе исчезает и появляется снова;
- startup с сохранённым A и новым B: A восстанавливается, B сразу сохраняется;
- late browser window после первой restore-волны;
- одинаковые fingerprints на разных десктопах и title-only → domain upgrade;
- перенос/новое окно непосредственно перед обычным Exit и session-end;
- финальная транзакция с нулём окон;
- Chrome-only и Edge-only не изменяют Firefox retention;
- retry success/failure не перезаписывает destination до подтверждения;
- atomic-write failure сохраняет старый snapshot и dirty state;
- corrupt primary выбирает valid backup;
- partial read и oversized mozLz4/SNSS отклоняются;
- чистая picker-state модель различает current, selected и active row;
- refresh после Ctrl+Click сохраняет search и scroll;
- target identity mismatch отменяет move.

### 12.2 Сборка и статические проверки

- `build-test.bat` — полный pure-logic regression suite;
- `build.bat` — x64 release-like сборка приложения;
- компиляция остаётся без новых warnings;
- целевой code review проверяет ownership Win32/GDI/COM handles, shutdown и границы файлов.

### 12.3 Ручная Windows QA

1. Открыть popup и проверить независимую подсветку current desktop, selection и foreground target.
2. Выполнить `Ctrl+Click`: окно и Windows переходят на целевой десктоп, popup остаётся, обе активные подсветки обновляются.
3. Повторить перенос тем же открытым popup.
4. Проверить обычный click, `Esc`, outside click, поиск, wheel и tooltip.
5. Проверить обе footer-ссылки.
6. Запустить Firefox при открытом Chrome и вернуть одно закрытое окно при другом открытом окне.
7. Проверить startup с сохранёнными и новыми окнами.
8. Сделать 100 циклов open/resize/close popup и убедиться через `GetGuiResources(..., GR_GDIOBJECTS)`, что количество GDI-объектов стабилизируется, а не растёт на каждом цикле.
9. Смоделировать недоступный/повреждённый layout и проверить backup/предупреждение без ошибочных переносов.

Реальные virtual-desktop COM-переходы и поведение Explorer требуют проверки в интерактивном сеансе Windows; unit tests покрывают детерминированные решения вокруг них.

## 13. Критерии приёмки

- Текущий десктоп и активное окно однозначно видны в popup одновременно с выбранной целью.
- `Ctrl+Click` переносит target, переключает desktop и не закрывает popup.
- Footer показывает утверждённый текст и две правильные ссылки.
- Все окна включённых Firefox/Chrome/Edge отслеживаются независимо.
- Новые окна сохраняются после restore, а повторно появившиеся сначала возвращаются в сохранённое место.
- Закрытое окно доступно до 30 суток и удаляется на границе 30 суток.
- Обычный Exit и Windows session-end выполняют финальный snapshot, включая случай нуля окон.
- Partial/corrupt write не уничтожает последнюю валидную раскладку.
- Массовый restore не использует `Sleep` на UI-потоке.
- Повторное изменение размера popup не увеличивает GDI handles на каждом цикле.
- Existing tests и новые regression tests проходят, приложение собирается без новых warnings.

## 14. Вне объёма

- Persistence окон приложений кроме Firefox, Chrome и Edge.
- Сохранение экранной геометрии, размера или monitor placement.
- SQLite, Windows service, browser extension или полноценная event-hook архитектура.
- Замена undocumented virtual-desktop COM интерфейсов публичным API, которого нет.
- Переименование legacy data directory/registry paths с риском потерять настройки пользователей.
